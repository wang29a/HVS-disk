# 更新执行器性能核验（2026-11-17）

用户要求核验读写接口与每插入I/O回合、计时内非生产开销、1000次插入的阶段分解，以及同机同盘的上游OdinANN单空间吞吐参照。用户明确选择：当前exact首轮完成后暂停后续E1重复与消融，优先运行本核验。`pause_at_e1_boundary.py` 只在该轨迹的全部检查点和归档完成后停止所属协调器，保留已完成图和结果；不会中断exact首轮。核验独占同一全局实验锁。

当前被核验的代码已发布至 `wang29a/HVS-disk` 的 `codex/dual-space-update-checkpoint` 分支，提交 `2fa563f9e0717b4b3b526c190a58943e890b85ec`。所有性能观察在独立源副本中生成，当前E1执行器、图、GT和已有库不修改。`prepare_profile.py` 验证冻结源码哈希，只加入时钟与线程私有计数器；原始与观察版本先在10k小图、单线程100次插入上核验图、坐标和正常退出快照逐字节一致。

正式样本使用同一个180万Laion初始B图和同样的前1000个新增向量。PQ与exact各做三轮，旋转lean驱动、原E1内存记录/进度驱动、阶段观察驱动的顺序。1000点样本是初始180万图后的前1000点，不代表全部20万更新过程的平均；母图密度随更新变化，分解结论限定于这一状态。另用仅关闭原有计时/I/O计数/度数遥测的诊断控制，保留全部算法锁、入度修改、保边和提交检查，以估算既有统计开销。主分解保持四更新加四查询线程、CPU72–75、NUMA3、L=96与rerank=96。所有结构/GT检查、文件准备、加载、fsync、JSON输出和快照都在插入区间外；计时前完成夹具复制与fsync。另做四更新、零查询的纯插入，避免把单空间无查询参照直接与混合负载比较。

主阶段为准备与坐标/PQ、候选搜索、新点剪枝、新点拓扑写入、反向边读改写、提交与入口维护、操作私有对象清理。满度重剪是反向边阶段的子项；页锁等待、入度互斥等待/持有和I/O是叠加观察，不能与主阶段直接加总。占比以同一批1000次插入累计延迟为分母。三轮时间比估计记录开销与插桩扰动，不把负估计当成机制带来加速。入度保护和状态维护是当前正确性方案的生产工作，单独量化而不删除它们来制造快基线。

上游固定为 `https://github.com/thustorage/PipeANN` 官方 `0.1.1`，提交 `7840ce96ac74a461b8efe2739b6aed5b14c15b9a`。使用Git对象导出的完整源码，Linux上源文件保持不变，CMake采用上游支持的 `USE_AIO=ON`，原生 `BG_IO_THREAD` 和 `DELTA_PRUNING`。node3内核为3.10；核验记录io_uring_setup结果，不将AIO路径称作io_uring。构图使用原生Vamana、180万Laion图像向量、R=40、L=200、64B PQ、无归一化，最多16构图线程、CPU72–87、NUMA3。原生码本与图不同于双空间DEG，结果只作实现吞吐参照，不声称严格同算法加速比。

OdinANN测量四插入线程、零查询线程、1000次插入、三轮。分别记录API返回和所有后台写入完成的吞吐：通过公开pop_query_buf接口收齐两倍配置线程数的工作缓冲作为屏障，缓冲只有在后台写入完成后才归还；队列为空不能代替此屏障。最终fsync在吞吐计时之外。上游4KiB同页单空间布局与当前8KiB分离双空间布局分别记录，不混淆物理I/O量。

三轮纯插入exact的吞吐与混合负载存在稳定差异，另用 `run_pure_probe.py` 在主套件完成后追加一次1000点、四更新线程、零查询线程的插桩重放。该样本用于观察阶段和锁等待，不替代三轮未插桩的纯插入吞吐，也不将负载变化视为已隔离的因果解释。追加样本同样独占全局实验锁。

运行入口是 `run_suite.py`，开始前必须已有暂停确认和既有node3上游库/冻结输入。它持有 `budget-reorder-20261103/queue.lock`，按序生成观察副本、构建、验证、测量和汇总；任何失败停止。`READY` 是准备完成的调度门槛，不作为实验成功标记。`analyse.py` 仅从原始测量重建结果；尚未完成的上游参照不会填预测数字。运行产物、数据、图和下载源码均留在忽略的runtime/上游目录，不提交Git。
