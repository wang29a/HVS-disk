# Laion hot-data diagnostic: Merge-2 versus No-alpha

This experiment tests whether lower PQ computation can make Merge-2 competitive when storage waiting is removed. It is a mechanism diagnostic; an all-hot result is not evidence of an SSD end-to-end win. Both outcomes are retained. The existing four-dataset concurrency and fixed-alpha experiment is reused, not rerun.

Node3 experiment root: `/mnt/nvme3/wz/hvs-disk-build-20261027/experiments/hotdata-alpha/`. Tmux session: `hvs-hotdata-alpha-20261028`. Live files are `status.json`, `logs/queue.log`, per-run logs/results, `analysis/validation.json`, and `analysis/summary.json`.

Completed on 2026-10-28 at 22:51:45 CST: all 36 runs and 324 measured points passed completion checks; all six parity checks passed. The temporary 45.5 GiB memory images were released. See [RESULTS.md](RESULTS.md): no reliable matched-recall Merge win was established. The apparent 0.7% all-hot/T1/Recall90 mean gain is smaller than repeat variation and depends on one slow No-alpha repeat. Timestamp-aligned pidstat identifies low CPU supply in 22 of the 156 all-hot points; no points are removed. Formal measurement plus intervening loading/warm-up took about 88.6 minutes; total launch-to-finish time was about 102.4 minutes.

The search implementation remains the unchanged static library from clean commit `d2a39e2bd50e6d03716c4268f7b90f931e5a6a1e`. A standalone `HotReader` derived from `LinuxAlignedFileReader` serves original aligned requests by `memcpy` from read-only, prefaulted tmpfs images. No graph, range, PQ, alpha, distance, rerank, or result-ordering code is changed. The memory backend completes topology requests synchronously and supplies matching completion notifications; eliminating asynchronous storage latency is part of this diagnostic and must be disclosed. Original native I/O fields remain logical requests, not physical storage reads; additional counters distinguish memory-served requests from SSD submissions.

The dataset is the already validated Laion index with 10,642,155 nodes and 512+512 float dimensions, two 64-byte PQ codes per node, degree 40, independently validated Starling layouts, K=10, beam=4, mem_L=0, strategy=17, full retained-candidate rerank. Both methods share the exact coordinate and PQ sources. Query alpha is the existing constant 0.7 array with its existing 1,000-query GT. No GT is recomputed, and replays do not increase the number of independent queries.

Long-running work is pinned to four physical CPUs `32,35,39,41` (NUMA 1; no sibling threads), selected after checking physical/sibling idleness. Search uses only T=1 or T=4. `OMP_THREAD_LIMIT=4`, explicit OpenMP places, BLAS threads=1, nice=10 and low-priority disk I/O apply throughout the serial tmux queue. Memory allocation is interleaved across NUMA 0,1. This placement differs from the older broad CPU-node binding, so this queue includes its own small SSD control rather than substituting old QPS values. Short compilation/checks can run normally; the search queue never expands to other cores.

One sequential loader stages about 45.5 GiB of shared tmpfs images (one coordinate source and both topology files), capped at 128 MiB/s. Independent SHA256 of each copy is verified. Each backend has the same 64 GiB image allowance and a 64 GiB peak-RSS check after each point; the kernel enforces an 80 GiB address-space limit. Both all-hot layouts fit fully, so there is no selective cache advantage. Every process prefaults its selected images and verifies residency outside timing. On completion or handled failure, only this queue's named tmpfs copies are removed; original indexes are never modified or removed.

Before timed runs, Merge and No-alpha each compare three L values (40,100,200) against the old driver. The new SSD path must match Recall, hops, PQ comparison counts and native request counts; all-hot and coord-hot must additionally produce byte-identical per-query IDs and exact distances to the new SSD path. Backend request accounting must agree with the logical search counts. Failure stops before formal measurements. These parity checks do not regenerate GT.

All-hot runs use L=20,40,50,60,70,80,100,120,140,160,200,300,400. Coord-hot and SSD controls use L=50,60,70,100,120,140,160 to bracket existing Recall@10=90%/95% operating points. Each backend tests both schemes at T=1/4 with three repeats. This is 36 serial search processes and 324 measured points. Methods and thread order alternate across repeats. Each L has a separate full 1,000-query warm-up; calibration is excluded, and each accepted continuous replay lasts at least ten seconds. Nominal timed duration is at least 54 minutes, plus staging, verification, loading and warm-up.

The three backends are all-hot (topology and coordinates resident), coord-hot (only coordinates resident; topology stays on SSD), and SSD (original aligned Linux AIO calls). Backend order is fixed in that sequence, so cross-backend timing can be affected by external load/time drift; within-backend method comparisons are the primary result. Every run saves p50/p95/p99 and mean external entry-to-return latency, original internal timing fields, RSS, comparisons, and logical/memory/SSD request counts. The older internal `total_us` excludes query-buffer/PQ preparation; it must not replace the new external latency. Original phase timers are retained but not summed into a complete latency decomposition.

Timestamped iostat/mpstat cover the formal queue, and pidstat records each search PID. A matched-recall summary is emitted only after a full three-repeat curve is available; interpolation stays within observed recall and does not extrapolate. Close means or noisy repeat results are not evidence of a statistically established win. A failed comparison is retained equally with a successful one.

To inspect the session, use `ssh node3` then `tmux attach -t hvs-hotdata-alpha-20261028`. To resume an interrupted queue, run `bash scripts/run.sh` from the remote experiment root inside tmux; completed JSON tasks are skipped only after identity checks, and the queue lock prevents concurrent runners. The scripts require Python 3, GCC11, libaio, jemalloc, OpenBLAS and the prior build artifacts at their recorded paths.

Run `python3 scripts/analyze_results.py` to generate `RESULTS.md` and `analysis/comparison.json` from completed raw runs. It only compares full three-repeat curves and preserves negative as well as positive outcomes. `logs/test-hot-reader.log` records a separate four-thread synthetic backend check for exact copied bytes, counters, out-of-bounds reads and completion accounting; it creates no dataset GT.

`python3 scripts/audit_completed.py` checks all 324 points, identities, backend recall consistency, peak RSS and pidstat intervals before regenerating the report. Local `completed-evidence.tar.gz` contains the complete remote experiment; `raw/` is its extraction. To regenerate from that extraction, run `python3 raw/scripts/audit_completed.py` followed by `python3 raw/scripts/analyze_results.py`. The report is written inside `raw/` in that case. CPU-supply flags are diagnostic observations, not grounds for deleting slow repeats or proof of a specific competing process.
