# Laion 六格过滤复测

本轮只复测精确导航 DRAM、PQ＋精排 DRAM、PQ＋精排 SSD 各自过滤开／关，主工作点为 95% Recall@10。Laion 使用已有的固定 α=0.5 和 α=0.1 两套查询与各自 GT，各 1,000 条查询。它不是 mixed-α 实验，也不包含密度、旁表、Starling、共享缓存或单空间对照。

所有搜索使用同一张重新构建的全量图、相同入口点、原始 ID 顺序、64-byte/空间 PQ、beam=4 和精排实现。查询内页缓冲保持 16 MiB/线程；跨查询共享缓存关闭。搜索固定四线程，CPU 72–75、内存 NUMA 3。构图先对 200,000 节点分别测试 16／24 个物理核，再用更快的配置测试 1,000,000 节点；正式图使用正常 `HybridIndex.build` 入口，覆盖 10,642,155 个节点。短测图仅估算成本，不能作为全量科学结果。

构图使用 OpenImages 统一目标实验已校验的修复库：两空间 L2 各自开方后再按 α 融合；`mergeIntervals` 包括最后一个区间；磁盘端点向外 floor／ceil，不缩窄浮点源区间。PQ 导航也先分别开方再融合；精确导航和精排使用同一目标。没有新增额外归一化。

全量构图前先用固定随机种子抽取 32 条查询，对两个权重分别在整个库上做 float64 穷举，核对已有 GT。已完成核验中，两个权重的 GT top-10 与统一目标均为 100% 重合；平方融合与开方融合之间的平均 top-10 重合率分别为 87.1875%（α=0.5）和 93.125%（α=0.1）。这验证 GT 语义，不能证明过滤性能变化的原因。原始双向量与复用的坐标文件逐值核验；末页只有一个有效向量，另外半页必须为零。

全量浮点图检查点放在 nvme2；新 Full 拓扑放在 nvme3，并复用经过核验的 43.59 GB 原始坐标，避免复制。写拓扑前核对实际槽数、页密度与可用空间；空间不足会保留源图检查点并显式停止，不会擅自删除旧数据或换盘计时。DRAM 查询前要求 NUMA 3 至少有 80 GiB 空闲；全量构图按短测峰值 RSS 外推检查内存。

两套工作负载使用同一个 seed=20261111 的查询划分，各 500 条调参、500 条报告，彼此不相交。先粗扫 L=40/80/160/320；PQ 同时粗扫 r=40/80/L（不超过 L），按调参召回不足才扩展 L=600/1000/1600/2400/3200。在调参集 95% 交叉附近补一个 L 中点，并补 r=20/40/60/80/120/160/240/L。精确导航没有精排阶段，记录的有效 r 为 0。

按调参集的两个确定性规则冻结配置：先页数后导航评估数、先导航评估数后页数；都不用延迟挑最优。冻结 90/92/94/95/96/97/98% 调参召回带的代表配置，并保留非支配前沿。精排的精确距离评估单独报告，不把一次 PQ 评估和一次精确评估等价相加。这两条规则不是全局最优延迟调参。报告集只用于三轮轮换顺序的计时和诊断，在实测曲线范围内插值 95%，未夹住则标记 UNCOVERED，不外推。

每个计时点单独预热，随后至少计时 10 秒；循环回放只延长计时，不增加独立查询数量。保留 L/r、展开节点、PQ／精确导航／精排各空间距离调用、真近邻发现／候选／精排覆盖率、拓扑与坐标提交页和去重页、各自提交等待时间，以及 QPS 和原始 p50/p95/p99。尾延迟只报告原始点，不插值。DRAM 的“提交页”是软件供页请求，不是 SSD 物理读取；等待时间除页数是批量摊销成本，不是 NVMe 单页延迟。

正式运行前逐边比较完整浮点源图与新 Full 拓扑，核验节点／邻居顺序、区间覆盖、槽数、零填充和部分末页。两种过滤设置分别验证 DRAM／SSD 的搜索轨迹、结果 ID 和距离逐位一致，并独立重算部分返回距离。计时点记录运行期 NUMA 证据和外部 CPU／磁盘活动；资源等待有界，外部干扰最多尝试三次，未验收点记入 pending，其他点继续，最后有限补跑。进程超时包含 Laion 大镜像加载，设为 900 秒。

本地边界验证入口为 `python3 scripts/test_protocol.py`；8 项检查覆盖完整页、部分末页、跨批次末页、向量损坏、非零 padding、禁止召回外推、保留配置端点及禁止额外实验臂。C++ 驱动和 Full 写入校验工具需在 node3 编译，另有参考格式逐字节比较和损坏输入拒绝检查。

远端工作目录为 `/mnt/nvme3/wz/hvs-disk-build-20261027/experiments/laion-six-cell-20261111`。`scripts/preflight.py` 执行前置校验与成本短测，`scripts/run_queue.py` 在同一全局锁下接续全量构图和搜索；可从检查点恢复。队列在 tmux `hvs-laion-six-cell-queue-20261111` 后台运行。重新运行可使用下面命令，启动前应检查已有 session，避免重复提交：

```bash
cd /mnt/nvme3/wz/hvs-disk-build-20261027/experiments/laion-six-cell-20261111
tmux new-session -d -s hvs-laion-six-cell-queue-20261111 \
  'env LC_ALL=C OPENBLAS_NUM_THREADS=1 python3 -u scripts/run_queue.py >> queue.log 2>&1'
```

读取 `status.json` 看当前阶段，`queue-status.json` 看全局锁状态，`analysis/build-cost-estimate.json` 看实测外推。每组权重的 `workloads/alpha-*/progress.json`、`analysis/pending-measurements.json` 和 `analysis/six-cell-summary.json` 分别记录进度、待补项和汇总。最终结论需要完整三轮验收和目标召回覆盖，不能把任务已入队当作结果已完成。

第一组精确导航的训练集关过滤 `L=40` 已有 95.28% 召回，报告集为 95.54%，因此原粗网格缺少 95% 下界。`scripts/coverage_extension.py` 在同一全局锁下、原队列之后，对两种权重、两种过滤设置统一补 L=24/32（入口点有 22 个，故不使用小于入口数的 L）；PQ 对应补 r=20/L。保持同一查询划分和两条确定性调参规则，重新冻结训练前沿，复用参数相同的已验收三轮结果，只测新增配置。原冻结协议与结果保留，新协议和汇总带 `-coverage-v2` 后缀，不能将旧点外推至 95%。追加队列为 tmux `hvs-laion-six-cell-coverage-20261111`，状态见 `coverage-queue-status.json`。
